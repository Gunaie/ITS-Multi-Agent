# ITS 项目面试常见问题及答案 (Q&A)

本文件按照从易到难的顺序，整理了在技术面试中可能遇到的关于本项目的问题。

---

## 🟢 初级：基础架构与选型

**Q1: 为什么要选择 FastAPI 而不是 Flask 或 Django？**
- **A**: FastAPI 原生支持 `async/await`，非常适合处理像 LLM 调用这种高延迟的 I/O 密集型任务。此外，它的 Pydantic 校验和自动生成的 OpenAPI 文档大大提升了开发效率。

**Q2: 什么是 RAG？在这个项目中是如何体现的？**
- **A**: RAG 即检索增强生成。在本项目中，当用户询问技术问题时，系统先去 ChromaDB 向量库中检索相关的技术文档片段，然后将这些片段作为背景知识喂给 LLM，从而避免大模型的幻觉。

**Q3: 为什么前端使用 SSE (Server-Sent Events) 而不是 WebSocket？**
- **A**: SSE 更加轻量，且天然支持单向流式传输（服务器到客户端），非常符合大模型逐字生成的场景。WebSocket 虽然支持双向，但实现和维护成本更高。

## 🟡 中级：智能体与工程化

**Q4: 多智能体 (Multi-Agent) 架构相比单 Agent 有什么优势？**
- **A**: 
  - **专业化**：不同 Agent 拥有不同的 Prompt 和工具集，降低了单个模型的干扰。
  - **扩展性**：可以方便地增加“财务专家”、“物流专家”等而不影响核心调度逻辑。
  - **长上下文管理**：通过任务交接，可以有效控制单个 Agent 接收到的 Context 长度。

**Q5: 你是如何解决 Agent 响应速度慢的问题的？**
- **A**: 
  - **并发处理**：在 `Service Agent` 中使用 `asyncio.gather` 并发请求地图数据和本地库。
  - **批量调用**：将百度地图路网距离计算从多次单点请求优化为单次批量请求。
  - **流式输出**：通过 SSE 让用户在模型生成第一个字时就能看到反馈。

**Q6: 如何实现会话持久化？Redis 在这里起什么作用？**
- **A**: 我们自定义了 `SimpleSession` 类，并使用 `pickle` 将其序列化后存入 Redis。Redis 不仅作为分布式缓存，还通过有序集合 (ZSet) 维护了用户的历史对话列表，实现了多端登录下的会话同步。

## 🔴 高级：算法、评估与可观测性

**Q7: 如果向量库检索出的内容不准确，你该如何优化？**
- **A**: 
  - **混合搜索**：结合 BM25（关键词）和向量检索。
  - **重排序 (Rerank)**：引入交叉编码器对初筛结果进行精细打分。
  - **分段策略**：调整 Chunk Size 和 Overlap。

**Q8: 你是如何量化评估 Agent 系统的好坏的？**
- **A**: 我们引入了 **Ragas** 框架。通过 Faithfulness（回答是否基于上下文）、Answer Relevance（回答是否切题）、Context Precision（检索是否精准）等指标进行量化分析，而不是仅凭感觉。

**Q9: 什么是 MCP (Model Context Protocol)？为什么要用它？**
- **A**: MCP 是 Anthropic 提出的标准协议，允许模型安全地访问本地或远程工具。我们通过 MCP 接入了联网搜索功能，使得 Agent 无需修改代码即可获得实时信息获取能力。

**Q10: LangSmith 在你的项目中扮演了什么角色？**
- **A**: LangSmith 提供了全链路追踪。在多 Agent 系统中，任务交接可能非常复杂，LangSmith 让我能看清 Orchestrator 在哪一步发生了意图识别错误，从而精准优化 Prompt 模板。

## 🟢 初级：位置服务与数据工程

**Q11: “附近维修站”功能的位置感知是怎么实现的？前端定位来源不可控怎么办？**
- **A**: 我设计了**多坐标系定位契约**。同一个地点在 WGS-84（浏览器 GPS）、GCJ-02（高德/腾讯）、BD-09（百度）三套坐标系下数值差几百米且肉眼无法分辨，程序无法自动判断来源。因此约定前端传坐标时携带前缀（如 `wgs84:30.59,114.31`），后端统一转换为百度坐标系；同时兼容纯文本地点（自动地理编码）。定位解析按“会话缓存 → 前端坐标 → 文本地点 → IP 定位（仅公网）”的优先级降级，全链路失败时 Agent **主动追问**用户所在城市，而不是静默兜底到北京——静默兜底会导致用户拿到完全错误的结果还不自知。

**Q12: 官方授权库的数据是怎么来的？免费配额只有 100 次/天怎么完成全国采集？**
- **A**: 我写了一个全国 76 城市的采集脚本，核心是四个机制：
  - **逐城入库**：每城抓完立即落库，任何时刻中断都不丢数据；
  - **配额熔断**：一遇到 API 返回 302 限额立即停止，避免无效请求刷满错误日志；
  - **断点续传**：已完成城市写入缓存文件，重跑自动跳过，第二天配额重置后从断点继续；
  - **幂等写入**：以网点名+地址哈希为唯一键，配合启动时的表结构自动迁移，重复导入零副作用。

## 🟡 中级：数据质量与 Agent 行为工程

**Q13: 地图检索返回的 POI 鱼龙混杂（第三方维修店、甚至无关店铺），如何保证“官方维修站”结果可信？**
- **A**: 纯字符串判断不可靠（我最初按地址里“路/街/号”出现次数判断，误判率很高），后来改为**加权评分模型**：
  - 电话归一化匹配官方库，权重 0.6（电话是最强证据，做了座机区号/400 号段归一化）；
  - 名称相似度 0.25（编辑距离 + 品牌词校验）；
  - 地址分词 Jaccard 相似度 0.15。
  - 达到阈值即判官方并回填官方库全字段（修正地图侧的错误坐标/电话），并对结果做合并去重（电话一致，或名称相似且物理间距 < 150m）。
  最终输出分级展示：✅ 官方授权店 / ❓ 疑似官方 / ⚠️ 第三方参考，让用户自己保有判断权。实测武汉 26 个 POI 中，官方授权库命中的网点全部自动标 ✅，而蕾特恩祛痘、华为服务中心、加油站便利店等无关噪音全部被正确低分排除。

**Q14: 你遇到过模型“幻觉调用”不存在工具的情况吗？怎么解决的？**
- **A**: 遇到过两类，都很有代表性：
  1. **提示词提及的工具名被当真调用**：我在提示词里写“禁止调用 `builtin_web_search`”，结果模型反而去调它——LLM 会把提示词中出现的工具名当作可用工具，哪怕语义是否定。教训是：**不在提示词里提及未注入/已移除的工具名**，工具选择交给工具列表的自然可见性。
  2. **多轮对话时模仿历史**：第一轮子 Agent 调用过 `get_nearby_official_repair_stations`，第二轮调度专家看到历史里的调用记录（temperature=0 确定性复现），直接调用自己没有的工具导致 500。我在会话层（自定义 `SimpleSession.get_items`）**过滤历史中的工具调用/返回条目**，只保留自然语言消息——单轮运行内的工具调用走内存不受影响。提示词约束对 temperature=0 的历史模仿无效，必须结构性切断信息的暴露。

## 🔴 高级：协议排障、依赖管理与质量体系

**Q15: 讲一次你最深的第三方协议排障经历。**
- **A**: 接入百炼 MCP 联网搜索时踩了四层坑，逐层递进：
  1. **SSE 端点废弃**：用标准 `MCPServerSse` 连接 `/WebSearch/sse` 返回空 body——百炼已下线 SSE 传输；
  2. **协议版本不兼容**：改用 `MCPServerStreamableHttp` + 最新协议版本返回 HTTP 500——百炼仅支持 `2024-11-05` 旧版协议；
  3. **自研兼容客户端**：两手都不通，我基于 HTTP POST 实现了轻量 MCP 客户端（initialize 握手 → tools/list → tools/call，协议头锁定 `2024-11-05`），稳定接入；
  4. **鸭子类型陷阱**：服务连上了但模型一直说“无法联网”。最终定位到 agents SDK 会直接访问 `server.use_structured_content` 属性，我的自定义类没这个属性 → 每次工具调用抛 `AttributeError` → 被 SDK 的 `failure_error_function` 吞成错误文本回给模型 → 模型以为工具坏了反复重试 → **Max turns (10) exceeded**。
  最终补上属性后，MCP 搜索首次在模型链路真正跑通。这个案例的收获是：**异常被中间层吞掉后，表象（Max turns）和根因（属性缺失）可能隔了很多层，必须逐层实证而不是猜测。**

**Q16: 依赖管理上踩过什么坑？**
- **A**: 注册接口 500，根因是 `passlib 1.7.4`（已停止维护）与 `bcrypt 5.0` 不兼容——passlib 内部的 72 字节探测逻辑触发了新版 bcrypt 的长度校验异常。锁定 `bcrypt==4.0.1` 解决，并在 requirements.txt 里注释了原因。教训：引入密码库这类“看起来装上就行”的依赖，也要有登录链路的 E2E 覆盖——我们的 E2E 套件第一次跑就抓出了这个问题。

**Q17: 如何系统性测试一个 LLM 多 Agent 应用？传统单测覆盖不了模型行为。**
- **A**: 我按测试金字塔分四层，并针对 LLM 特性做了特殊设计：
  - **纯逻辑单测（44 项，毫秒级，零依赖）**：评分算法、坐标转换、去重合并等确定性逻辑全部下沉到纯函数，让大部分逻辑不经过模型就能验证；
  - **工具冒烟测试**：真实 API 全链路（geocode → 并行检索 → 核验 → 距离）；
  - **API E2E（16 项）**：注册登录、四类对话场景、SSE 流式、严格 RAG、真实故障对话回放（路由泄漏/幻觉防复发）、会话历史去重，直接打 HTTP 接口；
  - **质量评测（25 项）**：自建规则断言 + 内容特征推断，覆盖路由/技术/服务/多轮/安全 5 大类。评测四维：路由正确率 84%、内容完整率 92%、安全合规率 100%、平均响应 4.24s。不依赖 LLM-as-judge，结果可控可解释。
  - **路由回归测试**：专测“实时资讯必须走 MCP 主搜索”这一条行为约束，且**免地图配额**可天天跑。
  LLM 特有的两个坑用工程手段规避：每个 E2E 用例用**唯一 session_id**（否则 temperature=0 下模型模仿历史产生假失败）；对百度配额敏感的场景做**配额预算管理**（每次运行消耗可预估、可拆分）。
