# 联想售后智能客服项目面试常见问题及答案 (Q&A)

> 本文件按**从易到难**分八档整理了 40 个面试问题。题目按面试官的追问路径设计:先考察项目理解,再逐层深入到工程细节与排障经历。每题答案都基于项目真实实现,标注了对应源码位置,便于对照复习。

---

## 第一档 🟢 基础认知(项目是什么)

**Q1: 用一分钟介绍一下这个项目。**

**A**: 这是一个面向联想品牌产品(ThinkPad/小新/YOGA 等)的售后智能客服系统,个人全栈开发。核心是**三模型多 Agent 编排**:一个规则意图网关把用户请求分成三类——纯服务诉求(如"附近维修站")直连服务专家秒答、复合意图(如"屏幕坏了帮我找维修站")先技术后服务合并回答、技术/闲聊类交给调度专家路由。技术专家走 RAG 知识库(500+ 售后文档)和 MCP 联网搜索,服务专家走百度地图 + 官方授权核验引擎。全链路 SSE 流式输出、LangSmith 追踪,47 项单测 + 16 项 E2E + 25 项质量评测,Docker Compose 6 容器一键部署。

**Q2: 为什么选售后客服这个场景?**

**A**: 三个原因:① 售后是 LLM 最适合落地的领域之一——故障排查是结构化知识(RAG 天然适配),网点查询强依赖外部工具(Function Calling 天然适配),两类需求都真实存在;② 有明确的可量化验收(路由对不对、检索准不准、距离对不对),方便做质量评测;③ 复合意图("电脑坏了+帮我找维修")天然考验多 Agent 编排,单 Agent 方案做不到位。

**Q3: 为什么用 FastAPI 而不是 Flask/Django?**

**A**: FastAPI 原生支持 `async/await`,非常适合 LLM 调用这种高延迟 I/O 密集型任务(单请求挂起数秒,异步才能撑起并发);Pydantic 做请求校验;自动生成 OpenAPI 文档;SSE 流式响应用 `StreamingResponse` 实现很自然。

**Q4: SSE 和 WebSocket 为什么选 SSE?**

**A**: 大模型逐 token 生成是**单向**服务器→客户端推送,SSE 轻量、基于纯 HTTP(天然过网关/代理)、自带断线重连语义;WebSocket 双向能力用不上且实现复杂。本项目 `/chat_stream` 用 SSE,历史会话管理等仍是普通 REST。

**Q5: 说说 RAG 的原理,项目里怎么用的?**

**A**: 检索增强生成 = 先检索后生成,用真实文档约束模型输出,降低幻觉。本项目:用户技术问题 → ChromaDB 向量检索 + Jieba 标题检索双路召回 → 去重重排 → 片段拼入 Prompt → glm-5.2 生成回答,回答标注来源文档。知识库是独立的 FastAPI 微服务(backend/knowledge),主后端通过 HTTP 调用。

**Q6: MySQL 里有哪些表?为什么这么设计?**

**A**: ① `users`:id/username/password_hash,存哈希不存明文(passlib+bcrypt,锁 bcrypt==4.0.1);② `service_stations`:官方授权网点库,name/phone/lat/lng(统一 BD-09)/city(来源城市)/source/**name_addr_hash(MD5(名称+地址)唯一键)**——哈希唯一键让采集脚本幂等(重复导入零副作用),配合启动时自动迁移表结构(缺列自动 ALTER)。

**Q7: Redis 在项目里起什么作用?**

**A**: 三件事:① **Agent 会话持久化**——自定义 SimpleSession 实现 SDK 的 Session 协议,JSON 序列化存 Redis(明确禁止 pickle:反序列化有安全风险且跨进程脆弱),支持 7 天过期;② **用户→会话列表**用 ZSet(score=最后活跃时间)支撑前端历史会话侧栏;③ **定位会话缓存**——GPS 24h/文本 2h/IP 30min 差异化 TTL,避免重复定位调用。

## 第二档 🟡 架构设计(为什么这样搭)

**Q8: 多 Agent 相比单 Agent 好在哪?什么场景该用?**

**A**: ① **专业化**:每个 Agent 独立提示词+工具集,指令冲突小(调度者提示词只管路由,技术专家只管排障);② **模型分层**:不同任务用不同模型,兼顾质量与成本;③ **上下文隔离**:handoff 时子 Agent 只带必要上下文,单 Agent 的上下文会无限膨胀。适用判断:任务有明显类型边界且各自需要不同工具/知识时才值得上多 Agent,否则是过度设计——简单客服一个带工具的 Agent 就够。

**Q9: 详细讲讲三分支编排怎么工作的?为什么这么设计?**

**A**: `classify_intent()` 规则网关(main.py,不走模型):
- **service_only**(短句≤30字 + 服务关键词)→ **直连**服务专家,省掉一次调度 LLM 调用(约1-2秒),响应快
- **compound**(服务关键词 + 技术词)→ **先技术专家后服务专家,合并回答**——这是真实用户反馈催生的:早期二分支方案里"屏幕坏了帮我找维修站"只会得到一半答案,丢需求
- **other**(技术/闲聊/模糊)→ 走调度专家,由模型判断回答还是 handoff
用规则而非模型做首层路由,因为服务关键词识别不需要智能,规则更快更稳定可测试。

**Q10: 为什么用三个不同模型?一个不行吗?**

**A**: 成本/能力按角色分层:调度要**准**但任务简单→qwen3.7-max 降低误路由;技术专家要**稳定 Function Calling**(绑知识库+搜索工具)→glm-5.2(需 extra_body 注入 tool_stream);服务专家是短查询+工具调用→deepseek-v4-flash 快且便宜。全用一个强模型成本高,全用便宜模型工具调用不稳。**加一个模型不只是加配置**:每个模型的接口行为有差异(如 glm-5.2 的 tool_stream),要做兼容性测试(test_model_compat.py)。

**Q11: Handoff(任务交接)具体怎么实现的?上下文怎么传?**

**A**: 基于 agents SDK 的 handoff 机制:Agent 定义里声明可交接的目标 Agent 列表,模型通过特殊工具调用触发转移,SDK 切换当前 Agent 并传递会话。上下文通过 Redis Session 共享(全量历史),同时我把定位等结构化上下文写在 `session.context` 里供工具函数读取。关键工程点:**会话历史要过滤子 Agent 的工具调用条目**(见 Q23),否则出幻觉调用。

**Q12: 为什么知识库和主后端分成两个微服务?**

**A**: 职责与生命周期不同:知识库是"数据密集型"(向量库/文档管道/ embedding),主后端是"逻辑密集型"(Agent/工具/会话)。分离后:① 各自独立部署重启,调 RAG 不影响线上对话;② 独立伸缩;③ 技术栈解耦——知识库可整体换成 LlamaIndex 而主后端不动;④ 边界清晰(RAG 质量问题只查 knowledge 服务)。代价是多一跳 HTTP 和一份部署配置,可控。

**Q13: 会话历史越来越长怎么办?有做上下文管理吗?**

**A**: 三层:① Redis Session 设置 7 天过期;② 结构化信息(定位等)放 `session.context` 单独管理 TTL,不进对话历史;③ 历史过滤策略——子 Agent 的工具调用/返回条目不入模型可见历史,显著压缩 token。目前没有做摘要压缩,是明确的后续优化点(长会话 token 成本会线性涨)。

**Q14: 流式输出是怎么实现的?中间有哪些事件?**

**A**: 后端 `Runner.run_streamed()` 拿到异步事件流,外层 `asyncio.timeout(120)` 兜底,把 `raw_response_event` 的 delta 逐个包装成 SSE `data:` 帧推给前端;前端 fetch ReadableStream 逐块解析渲染。要处理的细节:事件里区分文本增量/工具调用/handoff 切换(前端"思考过程"下拉框展示)、客户端断连清理、SSE 经过 nginx 需关 `proxy_buffering`。

## 第三档 🟠 RAG 深入(检索质量怎么保证)

**Q15: chunk 怎么切的?为什么?**

**A**: 按标题+段落切分(售后文档天然是"标题→故障现象→排查步骤→注意事项"结构),chunk 保留所属标题链(metadata 带 title/source),这样检索单个步骤时能带上上下文标题,生成时模型知道这段讲的是什么故障。没有用固定 token 滑窗——售后文档语义单元清晰,结构化切分优于机械切分。

**Q16: 向量检索不准,你做过哪些实际优化?**

**A**: 真实调优记录(每条都有前后对比):
1. **双路召回**:向量(top_k=8)+ Jieba 标题检索——"ThinkPad"这类专有名词 embedding 弱但关键词强
2. **标题规范化去重**:同一文档因向量召回(标题带"004-"前缀)和标题召回(不带)重复出现两次,占满返回位;规范化标题(去序号/后缀)后再去重
3. **同一文档只保留最高分 chunk**:修复前"电脑黑屏"返回的 4 篇里有 3 篇来自同一文档
4. **扩候选池**:向量 top_k 5→8,重排候选 15→20
5. **过时文档清洗**:向量库里混着 Windows7/联想手机时代的爬取文档,按标题关键词过滤清除 161 块,消除检索污染
效果:10 个故障类查询命中新增文档 10/10 且排名第 1;"黑屏"从只检索到 1 篇到稳定召回 4 篇不同文档。

**Q17: embedding 模型怎么选的?**

**A**: `text-embedding-v3`(阿里百炼)。选型逻辑:与 LLM 同一平台(API Key 通用、计费统一)、中文效果好、接口是 OpenAI 兼容风格;自部署 BGE-M3 需要 GPU 资源,个人项目不划算。设计上把 embedding 封装在知识库服务内部,换模型只动一处。

**Q18: embedding API 挂了怎么办?**

**A**: **平稳退化**:检索服务捕获 embedding 异常后自动退化为纯关键词检索(Jieba),服务不 503,只是召回质量下降。这是设计原则——售后场景"回答质量降级"远好于"完全不可用"。

**Q19: Ragas 评估怎么做的?指标怎么看?**

**A**: tests/evaluation/ 下基于 Ragas 搭了评估脚本,核心指标:Faithfulness(回答是否严格基于检索上下文,防幻觉)、Answer Relevance(是否切题)、Context Precision(检索是否精准)。当前 Faithfulness 保持 0.85+。同时自建了 25 项规则断言式质量评测(见 Q33)作为 Ragas 的补充——规则断言不依赖 LLM-as-judge,结果可解释、跑得快,两者互补。

**Q20: 知识库文档从哪来?怎么保证质量?**

**A**: 两个来源:① 爬取联想官方支持站点约 1000 份文档(清洗后入库 500+);② 针对高频场景人工编写 15 篇结构化排查指南(进水/蓝屏/黑屏/电池等)。质量治理:发现旧爬取文档混有 Windows7/联想手机时代内容会污染检索,写了按标题关键词的过滤清理流程;上传侧做了白名单校验(.md/.pdf/.docx/.txt)与同名检测。

## 第四档 🔴 Agent 行为工程(模型不可控怎么办)

**Q21: temperature=0 就完全确定了吗?你遇到过什么诡异问题?**

**A**: temperature=0 保证的是**给定相同输入输出确定**,但多轮对话的输入里包含**会话历史**——历史变了输出就变。真实案例:第一轮技术专家调过 `get_nearby_official_repair_stations`,第二轮调度者在历史里看到这条工具调用记录(temperature=0 精确复现模仿),直接调用**自己并没有的工具**导致 500。这教会我:**提示词约束对"模仿历史"无效,必须结构性切断信息暴露**(见 Q23)。

**Q22: 提示词工程上你踩过什么反直觉的坑?**

**A**: 两个:① **提示词里提到工具名会被当真**——我在技术专家提示词里写"禁止调用 builtin_web_search",结果 Flash 模型反而去调它(LLM 把提示词中出现的工具名当作可用工具,哪怕语义是否定)。解法:提示词不出现未注入/已移除的工具名,工具选择交给工具列表的自然可见性。② **反面引导同样危险**——服务专家提示词曾写"系统已持有坐标,location_hint 传空字符串",结果模型在用户明说"我在湖北工业大学"时也传空,忽略用户输入。解法:把指令改成正向表述"用户本轮明确提到地点时必须填入 location_hint"。

**Q23: 会话历史过滤是怎么做的?为什么不是全过滤或全保留?**

**A**: 在自定义 `SimpleSession.get_items()` 里过滤历史中的 tool_call/tool_output 条目,只保留自然语言消息。**不是全过滤**:调度者自己的交接记录必须保留,否则多轮后它忘记处理逻辑,只能干巴巴模仿文本;**不是全保留**:子专家的工具调用记录会诱导调度者模仿调用自己没有的工具。这是在"丢上下文"和"幻觉调用"之间调出来的平衡点。

**Q24: glm-5.2 的 Function Calling 静默失败是怎么回事?**

**A**: glm-5.2 走 OpenAI 兼容接口流式模式时,默认**不返回 tool_calls**——模型明明该调工具却直接编答案,没有报错,极难排查(表面是"模型不听话")。根因是该模型流式工具调用需要非标准参数:通过 openai_client 的 `extra_body={"tool_stream": True}` 注入后恢复。收获:接入新模型的第一个动作应该是**Function Calling 兼容性验证**(写了 test_model_compat.py),而不是先跑业务。

**Q25: "Max turns exceeded" 一次印象深刻的排障?**

**A**: MCP 服务连上了、客户端直连工具调用也成功,但模型链路里模型一直说"无法联网",最后 SDK 抛 Max turns (10) exceeded。逐层排查:SDK 对自定义 MCP server 类直接访问 `server.use_structured_content` 属性 → 我的鸭子类型类没这属性 → 每次工具调用抛 AttributeError → 被 SDK 的 `failure_error_function` **吞成错误文本回给模型**(不抛出!)→ 模型以为工具坏了重试 → 耗尽 turns。补上属性即愈。方法论:**异常被中间层吞掉后,表象与根因可能隔了很多层,必须逐层实证**——这也是我后来坚持"每层加分级日志(重试前2次 INFO、第3次 WARNING)"的原因。

## 第五档 🔴 协议与依赖排障(工程硬功夫)

**Q26: MCP 是什么?你为什么自己写客户端?**

**A**: MCP(Model Context Protocol)是 Anthropic 提出的模型-工具连接标准,initialize/tools/list/tools/call 三段式。自研原因:百炼平台的 MCP WebSearch 与标准 SDK 全不兼容——`MCPServerSse` 连 SSE 端点返回空(已废弃);`MCPServerStreamableHttp` + 新协议版本 HTTP 500(仅支持 2024-11-05)。于是基于 httpx POST 实现了鸭子类型客户端:协议头锁 2024-11-05、3 次重试分级日志、实现 `use_structured_content=False` 等 SDK 依赖属性。成本约 200 行代码,换来稳定联网搜索。

**Q27: passlib + bcrypt 的坑?怎么被发现和预防的?**

**A**: 注册接口 500,根因 passlib 1.7.4(已停维护)内部对 bcrypt 做 72 字节探测,触发新版 bcrypt(≥4.1)的长度校验异常。锁 `bcrypt==4.0.1` 解决并在 requirements.txt 注释原因。预防:这类"装上就行"的基础依赖要有登录链路 E2E 覆盖——我们的 E2E 套件第一次跑就抓出这个问题,证明 E2E 的价值。

**Q28: 容器化踩过什么坑?**

**A**: 三个典型的:① **开发命令进容器**:Dockerfile CMD 沿用 `python main.py`(内部 host=127.0.0.1 + reload=True)→ 宿主机映射端口连接全断;必须 uvicorn `--host 0.0.0.0` 且去 reload;② **假健康检查**:healthcheck 打的 /health 路由根本不存在,httpx 对 404 不报错 → 容器假 healthy,依赖它的服务带病启动;补真实路由;③ **混合模式代理**:容器前端访问本地后端必须用 `host.docker.internal:8001/8002`。另有一个诡异案例:同机另一项目容器占用 8001 端口,Docker Desktop 的转发言代理**绕过了端口冲突检测**,知识库流量被静默劫持(前端报查询错误但服务日志无异常),靠 `docker ps` 全量排查定位——教训是端口问题要查全局而不是只看报错服务。

**Q29: 镜像怎么优化的?**

**A**: 四招:.dockerignore 排除 .venv/data/cache(镜像 5GB+ → 1.3-1.7GB);Dockerfile 内配清华 pip 镜像源;**依赖层前置**(requirements 层与代码层分离,改代码不重装依赖,重建从全量到 5-10 秒);纯 Python loader 替代 unstructured[all-docs](避开 torch+CUDA 数 GB 依赖)。

## 第六档 🟠 定位与数据工程(项目的独特性所在)

**Q30: 前端定位来源不可控,坐标又不统一,怎么设计的?**

**A**: **多坐标系契约**:WGS-84(浏览器GPS)/GCJ-02(高德腾讯)/BD-09(百度)对同一地点数值差几百米且肉眼无法分辨,程序无法自动判断。约定前端传坐标必须带前缀(`wgs84:`/`gcj02:`/`bd09:`,默认 BD-09),后端统一转换;任何定位 SDK 都能无缝接入。百度 JS API 定位原生返回 BD-09,零转换。

**Q31: 完整讲讲定位解析链路。**

**A**: `location_service.resolve_user_location()` 四级降级:① **location_hint**(用户本轮打字说的地点,优先级最高——用户打字说的地方必须压过浏览器猜的位置,这是实际 badcase:浏览器 IP 定位到咸宁,用户明说"我在湖北工业大学"却被忽略);② 会话缓存(GPS 24h/文本 2h/IP 30min 差异化 TTL);③ 文本地理编码——从 hint 提取城市名传给百度 geocode 的 `city` 参数限定范围,并与 POI 名称检索**并行交叉校验**(geocode 粗精度或两者漂移>3km 时信任 POI——"湖北中医药大学黄家湖校区"曾被解析到同校昙华林校区,偏差 11.7km);④ IP 定位(仅公网客户端有效,服务器本机 IP 毫无意义)。全失败 → 返回 None,**Agent 主动追问**城市,禁止静默兜底默认城市——错误位置的用户拿到错误结果还不自知,比追问糟糕得多。

**Q32: 地图返回的 POI 鱼龙混杂,怎么保证"官方维修站"可信?**

**A**: **加权评分核验引擎**(纯字符串判断不可靠,最初按地址"路/街/号"出现次数判,误判率高):电话归一化匹配官方库 0.6(最强证据;座机区号/400号段/分机/多电话字段拆分,任一号码命中即通过)+ 名称相似度 0.25(编辑距离+品牌词)+ 地址 Jaccard 0.15。达阈值判官方并**回填官方库全字段**(顺带修正地图侧错误坐标/电话);去重(电话一致或名称相似且间距<150m);输出三级展示 ✅官方/❓疑似/⚠️第三方,把判断权留给用户。实测武汉 26 个 POI:官方库命中全标✅,祛痘店/华为店/加油站全被低分排除。

**Q33: 百度免费配额极小,76 个城市怎么采集的?**

**A**: 四机制:**逐城入库**(每城抓完即落库,任何中断不丢)、**配额熔断**(一遇 302 限额立即停,避免无效请求)、**断点续传**(已完成城市写缓存文件,重跑跳过,次日配额重置接着采)、**幂等写入**(name_addr_hash 唯一键+自动迁移表结构)。支持 `--cities 武汉` 指定城市、`--dry-run` 预览。核心思想:**把不可控的外部配额约束,转化为可分批、可恢复、可验证的工程流程**。

**Q34: "附近维修站"接口为什么快?做过什么性能优化?**

**A**: 串行版要 15s+:定位→检索→逐点测距全串行。优化:① 三关键词检索 `asyncio.gather` 并行(POI 召回 10→26 且不加耗时);② **批量 Route Matrix**——一次请求算完全部点位的路网距离,替代逐点调用(15s→5s 内);③ 全链路超时预算制(定位 4s+检索 8s+测距 6s,外层 22s 兜底),任何一环卡死不拖垮整体;④ 检索结果缓存于会话。平均响应从 15s+ 降至 4.24s(25 项评测均值)。

## 第七档 🔴 测试与质量体系(LLM 应用怎么测)

**Q35: LLM 应用的输出不确定,怎么系统性测试?**

**A**: 测试金字塔,关键思路是**把确定性逻辑从模型身边剥走**:
1. **47 项纯逻辑单测**(毫秒级零依赖):评分算法/坐标转换/去重合并/追问链路全部下沉为纯函数,大部分逻辑不经过模型即可验证
2. **工具冒烟测试**:真实 API 全链路(geocode→并行检索→核验→距离)
3. **16 项 API E2E**:注册登录/四类对话场景/SSE 流式/严格 RAG/**故障对话回放**(把 badcase 固化防复发)/历史去重
4. **25 项质量评测**:规则断言+内容特征推断,路由正确率 84%/内容完整 92%/安全合规 100%/平均 4.24s
5. **路由回归测试**:专测"实时资讯必须走 MCP 主搜索"这一行为约束,且免地图配额可天天跑

**Q36: 为什么质量评测不用 LLM-as-judge?**

**A**: LLM-as-judge 三个问题:结果不可复现(哪怕温度 0,judge 模型升级即漂移)、成本高、判分标准黑盒。我用**规则断言+内容特征推断**(如路由断言=日志中哪个 Agent 被执行;安全断言=输出不出现"联系联想客服人员"外的联系方式幻觉),100% 可解释可复现。代价是覆盖不了"回答好不好"这类主观维度——所以保留 Ragas(Faithfulness 0.85+)做主观质量基线,**两者互补而不是二选一**。

**Q37: E2E 测试有什么 LLM 特有的坑?**

**A**: 两个:① **必须用唯一 session_id**——temperature=0 下模型精确模仿会话历史,复用会话跑第二轮,模型输出被历史污染产生**假失败**(我们真实踩过);② **配额预算管理**——百度免费配额百余次/天,每次 E2E 消耗多少配额要可预估可拆分,路由回归类测试设计成完全免地图配额。另外 Windows 下 PowerShell Invoke-WebRequest 会把中文编码成 `???????`,导致模型无法识别意图——测试必须用 httpx 或浏览器。

## 第八档 🟣 开放与系统设计(高分区分题)

**Q38: 如果用户量上到千级并发,这个架构哪里先崩?怎么改?**

**A**: 按瓶颈顺序:① **LLM API 限流**——百炼 QPS 配额先顶住,需要多 Key 轮询/多供应商 fallback/请求排队;② **SSE 长连接**——uvicorn 单进程连接数有限,要多 worker+异步事件循环已备(asyncio),必要时把 SSE 网关换 nginx 直反或专用推送服务;③ **Redis/MySQL 连接池**——已有池化,需调大并加只读副本;④ **百度地图配额**——免费配额秒没,必须买商用配额+结果缓存(网点数据变化频率低,Redis 缓存命中率会极高);⑤ 无状态改造——会话已在 Redis,水平扩容后端是加机器的事。架构上微服务拆分已经为此铺好了路。

**Q39: 这个项目商业化还缺什么?**

**A**: ① **安全**:HTTPS、登录限流防爆破、AK 泄露防护(浏览器端 AK 收紧 Referer 白名单+配额限额)、prompt injection 防护(用户输入可能诱导工具滥用,需对工具参数做白名单校验);② **合规**:客服话术免责声明、用户数据隐私(会话加密存储/留存策略);③ **运营**:人工客服转接兜底(LLM 答不了的必须有出口)、满意度评价闭环、badcase 回流机制;④ **SLA**:超时降级(已经做了)+多区域部署。技术上最缺的是**转人工**和**反馈闭环**——真实的客服系统里,识别"我答不了"并优雅转出,比多答对几道题更重要。

**Q40: 如果重做一遍,你会改什么?**

**A**: ① **意图网关早该上**——最初的二分支设计浪费了两周才在用户反馈里发现复合意图丢半边,应该在设计期就列全意图矩阵;② **模型兼容性测试前置**——tool_stream 静默失败耗掉半天,接入任何新模型先跑 Function Calling 冒烟;③ **会话历史过滤策略一开始就设计进 Session 协议**,而不是幻觉 500 后补;④ **更早引入 E2E**——passlib 坑如果有登录 E2E,当天就能发现;⑤ **公网部署前置**——localhost 环境发现不了 IP 定位、Referer 白名单这类问题,灰度环境越早越好。总结成一句话:**这个项目最大的教训是"集成点(模型/协议/容器/第三方API)必须最先验证",而不是把业务逻辑写完再接。**
