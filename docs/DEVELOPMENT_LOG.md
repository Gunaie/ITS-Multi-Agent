# 联想售后智能客服项目全周期开发与验证记录

> 本记录按时间线还原项目从需求分析到最终交付验证的全过程,包括**每一次架构演进的原因、踩过的坑、修复方式与验证结果**。与 IMPLEMENTATION_GUIDE.md(怎么复刻)和 INTERVIEW_QA.md(怎么讲)互为补充。

## 〇、模型策略说明(为什么没有"训练"环节)

本项目定位为**工程应用项目**,模型策略是"云端 API 接入 + 分工适配",而非自训练:

- **不做训练的原因**:售后客服的故障知识来自文档(RAG 解决),意图路由是规则可解(网关解决),推理能力依赖前沿模型(API 提供)——三个问题都没有"必须训练"的必要;自训练需要 GPU 集群与数据标注,投入产出比不成立
- **模型工作量的真实所在**:① 选型验证(Function Calling 兼容性/流式行为/中文质量);② 接口适配(glm-5.2 的 tool_stream 非标参数);③ 行为工程(temperature=0 历史模仿、提示词与工具名交互);④ 分工编排(三模型按角色分配)
- 若未来要做训练,最合适的切入点是用开源小模型 Lora 微调意图分类器替换规则网关(已在改进规划中)

## 阶段一:需求分析与知识库建设

- **目标**:解决联想技术支持文档的智能问答问题
- **数据源**:抓取并清洗约 1000 份 `.md` 格式技术手册,清洗后入库 500+
- **技术决策**:
    - 向量化模型选 `text-embedding-v3`(与 LLM 同平台,API Key 通用;自部署 BGE-M3 需 GPU 不划算)
    - 搭建 `backend/knowledge` 独立微服务,实现向量库 + 关键词库混合索引
- **验证**:Playground 测试确认 embedding 模型离线时自动退化至 Jieba 关键词检索,服务不 503

## 阶段二:Agent 架构演进(三次迭代)

- **V1 单智能体**:所有职责一个 Prompt——提示词过长,地理位置识别频繁出错,工具选择混乱。结论:单 Agent 上下文膨胀后指令互相干扰
- **V2 Orchestrator 二分支**:引入调度专家,技术咨询/周边服务二分路由,采用多智能体协作(handoff)。调度选用响应快的模型
- **V3 三分支 + 三模型**(阶段七完成):增加意图网关直连分支与复合意图合并,模型按角色分工
- **验证**:四类路由场景全部正确(技术/服务/复合/闲聊),见阶段八质量评测

## 阶段三:外部工具集成与性能瓶颈突破

- **地图引擎迁移**:
    - 最初使用高德 MCP,API 调用频率受限且稳定性不足
    - 切换为**百度地图 REST API**,手动封装地理编码/周边搜索/路网距离工具
- **性能攻坚**:
    - 记录:初版"附近维修站"查询需 15 秒以上(串行:定位→检索→逐点测距)
    - 改进:三关键词检索 `asyncio.gather` 并行(POI 召回 10→26)+ 路网距离**批量 Route Matrix**(一次算完全部点位)
    - 结果:响应降至 5 秒内
- **坑**:百度 scope=2 时 `distance` 字段在 POI **顶层**而非 `detail_info` 内——读错位置得到 0 值污染排序

## 阶段四:功能修复与体验增强

- **SSE 修复**:解决 Raw Delta 解析逻辑不兼容导致的咨询平台无回复问题
- **会话加固**:Redis 增加 `session_meta` 结构,自动提取对话标题、会话类型自动识别
- **交互优化**:移除与浏览器冲突的 Ctrl+K 快捷键逻辑

## 阶段五:可观测性与评估系统建设

- **LangSmith**:接入全链路追踪,Agent 调度/交接/工具调用的输入输出全可视——后续所有 Prompt 调优的第一工具
- **自动化测试**:编写 `tests/integration/` API 集成测试
- **Ragas 评估**:对 RAG 效果做基准测试,Faithfulness 得分保持 0.85 以上

## 阶段六:服务网点能力重建与全链路质量建设(2026-08)

- **定位服务统一**:
    - 抽离 `location_service` 统一定位解析:会话缓存(GPS 24h/文本 2h/IP 30min 差异化 TTL)→ 前端坐标 → 文本地理编码 → IP 定位(仅公网)四级降级;全失败时 Agent 主动追问而非静默兜底
    - 设计**多坐标系契约**:前端传 `wgs84:/gcj02:/bd09:` 前缀坐标,后端自动转换百度坐标系
- **网点检索与核验重建**:
    - 三关键词(客户服务中心/授权服务站/维修)并行检索,POI 召回量从约 10 提升至 26
    - **加权评分核验**:电话归一化 0.6 + 名称相似度 0.25 + 地址 Jaccard 0.15;命中官方库回填全字段;电话一致或名称相似且间距 <150m 合并去重;输出 ✅/❓/⚠️ 分级展示
    - 距离口径修正:路网距离优先、直线兜底,明确标注,消除 `detail_info.distance` 读取错误导致的 0 值污染
- **数据工程**:幂等建库(name_addr_hash 唯一键 + 启动自动迁移 + city 来源字段);全国 76 城采集脚本(逐城入库、302 配额熔断、断点续传、`--cities`/`--dry-run`)
- **稳定性排障**(详见 INTERVIEW_QA.md Q21-Q26):
    - MCP 兼容三层修复:自研 POST 客户端(`2024-11-05` 协议)→ 补 `use_structured_content` 属性(缺失→每次调用 AttributeError 被 SDK 吞→模型重试至 Max turns)→ MCP 联网搜索**首次在模型链路真正跑通**
    - 模型幻觉调用治理:提示词不提及未注入工具名;MCP 就绪时自动摘除本地兜底工具(消除同名误选)
    - 多轮模仿治理:`SimpleSession.get_items` 过滤历史中的工具调用条目(temperature=0 下调度者曾模仿子 Agent 调用致 500)
    - 依赖锁定:`passlib 1.7.4` 与 `bcrypt>=4.1` 不兼容 → `bcrypt==4.0.1`
- **质量建设**:
    - 纯逻辑单测(评分/坐标/去重/追问链路)、工具冒烟测试、16 项 API E2E(健康/鉴权/会话/四类对话/流式/严格 RAG/故障对话回放/历史去重/清理)、联网搜索路由回归(免地图配额)
    - E2E 工程要点:唯一 `session_id` 防历史模仿假失败;配额预算管理

## 阶段十:维修站定位双坑修复(2026-09-01)

两个独立 badcase,根因不同:

- **Case 1 黄家湖校区**:"湖北中医药大学黄家湖校区"不含城市名 → geocode 不带 city 参数全国解析 → 命中同校**昙华林校区**(漂移 11.7km),最近店显示 3.36km(实际 13km)
  - 修复:geocode 与 POI 名称检索**并行交叉校验**(粗精度/漂移>3km 信任 POI);报告尾部标注定位口径
- **Case 2 湖北工业大学**:用户明说地点被前端粗定位静默覆盖——浏览器 IP 定位到咸宁,消息文本被跳过,服务专家提示词"location_hint 传空"又主动诱导忽略
  - 修复:文本窄提取始终执行,写入 `location_hint_pending` 优先于粗定位;服务专家提示词改正向表述;官方店最近距离>50km 强制预警;IP 兜底显式标注口径
- **验证**:E2E 模拟原始故障场景(咸宁坐标+文本"我在湖北工业大学")→ 定位武汉洪山区 ✓,最近官方店 4.47km ✓,无咸宁店混入 ✓
- **交付**:commit `c22626f`(6 文件,+178/-31)
